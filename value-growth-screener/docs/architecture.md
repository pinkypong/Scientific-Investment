## 1. 한눈에 보기

**VGS(Value-Growth Screener)가 본체입니다. 대시보드는 VGS 결과를 보여주는 화면으로 덧붙입니다.**

```
[외부 데이터]  SPY·Nasdaq-100 보유종목 / SEC 공시 / 일별 가격 / Bigdata.com
      │  수집  (vgs.data.*)   사실만 저장하고 출처·시각·해시를 같이 기록
      ▼
[사실 저장소]  value-growth-screener/data/   (Git에는 올리지 않음)
      │
      ▼
[VGS 엔진]
   Step 1  스크리닝      공시 숫자로 여러 종목을 훑어 후보를 고른다
   Step 2  종목분석      고른 종목에 사람의 가정을 더해 가치평가한다
   Step 3  원문 바로가기  재무제표 원문·뉴스·리포트 링크 (숫자 계산에는 쓰지 않음)
      │  결과: Markdown 리포트 / 순위 CSV / (예정) 대시보드용 JSON
      ▼
[화면]  지금: 터미널 리포트    덧붙이는 중: 대시보드 (Vercel, 모바일 조회)
```

한 문장으로: **"사실은 사실대로, 가정은 가정대로 따로 두고, 결론은 사람이 내린다."**

## 3. "단계"라는 말의 세 가지 뜻 (헷갈리지 않기)

| 이름 | 무엇의 단계인가 | 어디에 정의돼 있나 |
|---|---|---|
| **수집 N단계** | 데이터를 모으는 깔때기: 전 종목 → 상위 50 → 상위 20 → 최종 10~15 | `docs/collection-plan.md` |
| **화면 Step N** | 사용자가 보는 화면 구분: Step 1 스크리닝 / Step 2 종목분석 / Step 3 원문 바로가기 | 이 문서 |
| **작업 A, B, C…** | 우리가 만드는 순서 | 9장 |

**화면 Step과 수집 단계의 연결 (제안, 아직 확정 전):**

| 화면 | 수집 단계 | 하는 일 |
|---|---|---|
| Step 1 스크리닝 | 1단계(전 종목, 저비용) + 2단계(상위 50) | 공시 숫자로 후보 압축. 필터 기준은 사람이 조절 |
| Step 2 종목분석 | 3단계(상위 20) + 4단계(최종 10~15) | TTM 시계열, 구간 비교, fcff/ri/epv 시나리오 |
| Step 3 원문 바로가기 | 3·4단계에서 확인한 문서 | 링크만 제공. 숫자를 가져오지 않는다 |

## 5. 데이터 계약 (VGS가 읽는 JSON)

입력 JSON은 네 구역으로 나뉩니다. 엔진은 다섯 번째 구역 `computed`를 새로 만들 뿐, 앞의 구역을 고치지 않습니다.

| 구역 | 누가 채우나 | 예 |
|---|---|---|
| `security` | 수집 | 티커, 이름, 섹터, 통화 |
| `objective` | 수집 (공시·시장 관측) | 매출, 영업이익, 장부가치, `history.ttm_series` |
| `assumptions` | **사람** | 성장률, WACC, 목표 ROE, `cycle_groups` |
| `sources` | 수집 | 제공자, 문서 ID, 관측 시각, 연결된 필드 |
| `computed` | 엔진 | 시나리오 가치, 점수, 플래그 |

**가치평가 방법 4가지** (`assumptions.valuation_method`):

| 방법 | 쉬운 설명 | 사람이 반드시 넣는 가정 |
|---|---|---|
| `fcff` | 미래 현금흐름을 현재가치로 할인 | 성장률 경로, 목표 마진, WACC 등 |
| `ri` 잔여이익 | 장부가치 + 자기자본비용을 넘는 이익의 가치 | 목표 ROE, 자기자본비용, 배당성향 |
| `epv` 이익력가치 | "성장 없이 지금 이익이 계속되면"의 가치 | 정상화 매출, 정상화 마진, 세율, WACC (**기본값 없음**) |
| 상대가치 | PER 등 배수로 교차검증 | 목표 배수 |

**사이클은 엔진이 해석하지 않습니다.** 엔진은 최근 10년(40개 분기말)의 공시 rolling TTM을 그대로 보여주고(`objective.history.ttm_series`), 사용자가 `assumptions.cycle_groups`로 날짜 구간을 직접 묶으면 그 안의 평균·최저·최고만 계산합니다. 이 결과는 점수·플래그·판정에 영향을 주지 않습니다.

**점수와 판정(PASS/WATCH)은 "규칙 기반"입니다.** 입력은 공시 사실이지만 점수 구간과 가중치는 사람이 정한 값이므로, 사실이 아니라 규칙의 결과로 표시합니다.

## 7. 대시보드 (덧붙이는 화면)

### 7.1 만드는 방식: 정적 사이트
`index.html` 한 파일에 데이터를 **빌드할 때 미리 넣어** 두고, Vercel이 그 파일을 그대로 내려줍니다. 서버도 데이터베이스도 없어서 폰에서 빠르고, 비밀값이 브라우저로 내려가지 않습니다. 계산은 모두 빌드 때 파이썬이 합니다. 브라우저에서 엔진을 돌리지 않습니다.

### 7.2 메뉴가 작동하는 원리
```
[① 스크리닝] [② 종목분석] [Memory] …    ← 문 (버튼, data-v="step1" 같은 이름표)
      │            │           │
   v-step1      v-step2     v-memory      ← 방 (화면, <div class="view" id="v-…">)
```
`showView('step1')`은 "모든 방을 끄고 이름이 `v-step1`인 방만 켠다"입니다. 방을 일괄 처리하므로 방을 추가해도 JavaScript를 고칠 필요가 없습니다.

**함정:**
- `tab`이라는 클래스 이름은 Memory 전용 클릭 처리기에 걸린다. 다른 곳에서는 `stab` 등 별도 이름을 쓴다.
- HTML이 2벌(원본, `web_deploy` 사본)이고 같아야 한다. 테스트가 확인한다.
- 폰에서 메뉴 버튼이 8개가 되면 메뉴 높이가 94px → 134px로 커진다. 메뉴는 화면 위에 고정되어 있다.

### 7.3 목표 형식 (2026-10-15 사용자 구상)
```
상위 탭 = 섹터   [반도체·메모리] [기술] [헬스케어] [금융] …
                       │
하위 탭 =        [Step 1 스크리닝] [Step 2 종목분석] [Step 3 원문 바로가기]
```
- 현재 Memory 탭은 없애고, 그 내용(개요·시장·기업·밸류에이션·확률·논거)은 "반도체·메모리" 섹터 안으로 **옮긴다**(삭제가 아님).
- Home, Governance, 설계 등 나머지 메뉴의 위치는 미정(9장).
- 디자인은 사용자가 별도로 작업 중. 화면 구조(HTML)와 겉모양(CSS)을 분리해서, 구조 작업이 디자인 작업을 막지 않게 한다.
- **구조 개편은 VGS 결과 JSON 형식이 정해진 뒤에 한다.** 보여줄 데이터 없이 틀부터 바꾸면 다시 뜯게 된다.

### 7.4 현재 대시보드 상태
브랜치 `feature/dashboard-valuation-tab`(main에서 분기, 커밋 2개). "① 스크리닝", "② 종목분석" 빈 화면과 섹터 소탭 틀(`.stab`)만 있다. 기존 Screener·Memory·Governance는 그대로다.

## 9. 결정 기록과 열린 질문

### 결정
| ID | 날짜 | 결정 | 이유 |
|---|---|---|---|
| D-1 | 10-14 | 엔진은 사이클을 해석하지 않는다. TTM 원자료 + 사용자 구간 | 사이클마다 해석 기준이 달라서 고정 규칙은 오해를 만든다 |
| D-2 | 10-14 | EPV 정상화 입력은 기본값 없이 사람이 입력 | 정상화는 판단이다 |
| D-3 | 10-15 | 객관 근거 점수는 "규칙 기반, 가중치는 가정"으로 표시하며 유지 | 순위를 매기는 데 쓸모가 있다 |
| D-4 | 10-15 | 정의가 갈리는 파생치(ROIC·베타)는 고정 정의 1개와 공식을 같이 기록 | 출처 원칙 |
| D-5 | 10-15 | **VGS가 본체, 대시보드는 덧붙이는 화면** | 사용자 방침 |
| D-6 | 10-15 | Step 3은 링크만. 애널리스트 리포트도 링크로만 두고 그 숫자를 가져오지 않는다 | 원칙 1 (추정치 금지) |
| D-7 | 10-15 | 대시보드는 정적 사이트 유지. 시세만 실시간 | 모바일·Vercel에 적합 |
| D-8 | 10-15 | 대시보드 구조 개편은 VGS 결과 JSON이 정해진 뒤 | 데이터 없이 틀만 바꾸면 재작업 |

### 열린 질문
1. **섹터 분류 출처**: SPY 보유종목 파일의 섹터 열(익숙한 11개 섹터, 제3자 분류, 실제 파일 확인 필요) vs SEC의 SIC 코드(공시 기반이지만 400여 개로 잘고 낡음). 제안은 SPY 열 우선, 없는 종목만 SIC.
2. **VGS ↔ data_sources 관계**: SEC 수집이 중복. 한국 종목(OpenDART)을 VGS에 넣으려면 연결이 필요.
3. **Home·Governance·설계 메뉴**를 새 구조에서 어디에 둘지.
4. **기존 Screener**(메모리 4종 순위)를 Step 1과 합칠지.
5. **루트 `index.html`**(낡은 사본) 정리.
6. **CI에 VGS 테스트 추가**(지금 CI는 data_sources 테스트만 돈다).

| **F** | Step 1 표와 필터 | 폰에서 정렬·필터 |
| **G** | 실제 SEC 데이터 연결, 주 1회 자동 갱신, Vercel 반영 | 자동 실행 결과 |

디자인 작업은 E 이후 CSS 단계에서 합류한다.

## 11. 용어집

| 용어 | 쉬운 설명 |

| 정적 사이트 | 서버가 계산하지 않고 완성된 파일을 그대로 내려주는 웹사이트 |

| CI | 코드를 올릴 때 테스트를 자동으로 돌리는 장치 |
